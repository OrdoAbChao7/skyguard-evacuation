## 1. 交付目标与范围

主线：在观测不完整、人员有限的活动散场场景中，选择值得执行的核查动作，由真实 AgentArts 编排、人工审批、现场反馈，形成可追溯的辅助决策。

本轮必须同时回答：平台是否真实运行；推荐是否比可用基线更有价值；工作人员是否实际受益；异常是否被正确处理。测试数量、页面数量、Agent 数量不作为成果指标。

| 本轮必交付 | 完成证据 | 保持的边界 |
| --- | --- | --- |
| 一个真实 AgentArts 应用 | 应用版本、真实调用、工具回执、关联 Trace、完整闭环记录 | 本地 stub 不算实接 |
| 一个真实协作场地的小范围受控任务 | 工作流程确认、区域资料、独立参与者任务记录 | 不模拟成真实大型疏散成果 |
| 一套公平实验环境 | 独立环境、固定协议、强基线、消融、原始失败数据 | 合成结论仅适用于实验条件 |
| 一条可恢复业务链路 | 重启、超时、重复消息、stale、人员冲突用例 | 单实例起步，不承诺多实例一致性 |
| 可复现提交包 | 新环境复现、材料与数据映射、真实演示 | 不保证竞赛名次 |

本轮不安排自训练视觉大模型、真实无人机飞控、全场数字孪生、强化学习、多 Agent 框架重构。昇腾实机进入后续阶段，除非当届赛题另有硬性要求。保留现有预测与安全内核，不为演示修改安全判定。

## 4. W1：预算、参数与场景边界

### 4.1 一个预算判定实现，多个调用入口

拟新增 `backend/src/services/mvp/budget.ts`，由 `voi.ts`、`multi-voi.ts`、`investigation-session.ts`、工单派发入口共同调用。复用业务预算规则不等于复用疏散规划结果；独立 `validator.ts` 继续独立重建安全约束。

输入：已结算成本、有效预留、候选动作、当前时间、截止时间、人员可用状态、场景参数版本。返回 `eligible`、原因码、各维度余量、计算上下文版本。失败原因至少区分资源、人员时间、截止时间、动作数、人员冲突、参数缺失和上下文过期。

候选准入必须同时满足：

```text
spent_cost + reserved_cost + candidate_reserved_cost <= max_cost
used_attempts + reserved_attempts + 1 <= max_attempts
spent_person_minutes + reserved_person_minutes + candidate_person_minutes <= max_person_minutes
now + candidate_completion_bound <= deadline
staff is available AND route/skills/context are valid
```

资源成本采用场景声明精度的整数单位；时间用整数秒。分数只在展示时四舍五入，禁止以四舍五入后的值决定预算准入。零值、负值、NaN、无穷大、缺字段在 Schema 层明确处理。

区分三种时间：人员工作分钟、动作历时、端到端墙钟时间。多人并行时人员分钟可相加，墙钟时间不能相加；审批等待消耗墙钟，但不自动记为巡查工作时长。第一轮实验默认单个现场执行资源，避免过早引入并行调度复杂度。

### 4.2 推荐、审批、派发、执行分别检查

| 时点 | 处理 |
| --- | --- |
| 推荐 | 只做快照预检，不占用人员，不声称保证稍后可执行 |
| 创建待审批工单 | 保存候选成本和参数版本；等待任务不长期锁资源 |
| 人工审批 | 确认当前证据与预算；审批不能替代派发时复检 |
| 人工派发 | 原子检查最新 context、人员与预算，写入有限有效期预留和工单状态 |
| 接单/开始执行 | 再核对预留、人员和 context；预留过期则拒绝开始并要求重新确认 |
| 完成/失败 | 结算实际已消耗资源，释放未消耗预留；失败不自动免费 |
| 拒绝/取消/过期 | 释放未开始动作的预留，记录原因；在途任务不静默释放人员 |

不确定时长不能提供现实硬保证：用声明的估计上界做准入，记录实际超时与成本超支，停止后续自动安排并提示负责人。实际成本不得截断到预算值。对已开始的现场任务，截止超时只触发人工协调，不由系统假定工作人员已返回或动作已取消。

重试沿用同一业务动作 ID，但新的实际尝试计入成本和次数。仅网络请求重发、且此前副作用已完成时，不重复记为现场尝试。

### 4.3 场景配置迁移

- 扩展 `safety/types.ts`、`scenario.ts` 与 `data/scenarios/*.json`：覆盖权重、冲突处理参数、时效、成本单位、预算、版本、provenance、演示序列。
- 将场景 ID、区域 ID、演示观测从 `agentarts.ts` 和 `index.ts` 移出；服务根据加载场景生成上下文。
- 动作类型等领域枚举可留代码；具体场馆区域、面积、容量、动作参数必须来自场景。
- 旧实验用冻结代码和冻结配置复现；新 Schema 使用显式迁移，不能悄悄补默认参数后仍宣称使用原配置。
- 缺关键参数拒绝开启对应调查功能并说明错误；不能默认补成乐观值。参数取值变化同步 `VOI_MODEL.md`。

必要回归：余额 0.9/动作 1.0 拒绝；恰好等于预算允许；两个派发竞争同一人只成功一个；预留过期、重复反馈、失败结算、执行超时；换第二个合成场景无需修改 TS；未知容量保持不可用。完成后运行项目规定的测试、两个 demo 和 build。

## 5. W2：证据台账与可重建信念

### 5.1 证据结构

拟新增 `mvp/evidence.ts`，保留 `ingest.ts`、人工反馈和 provider 入口，统一转入证据台账。

| 字段组 | 最小字段与规则 |
| --- | --- |
| 标识 | `evidence_id`、`source_id`、`source_type`、`payload_hash`；同 ID 不同内容拒绝并审计 |
| 时间 | `observed_at`、`received_at`、`expires_at`；按观测时间判断新鲜度；时钟异常独立标记 |
| 归属 | `scenario_id`、`region_id`、`source_group`、`supersedes_id` |
| 内容 | 原始 payload、解析结果、单位、估计/实测/合成标记 |
| 质量 | `calibration_version`、参数版本、来源说明；置信度不能由 LLM 改写 |
| 追溯 | `work_order_id`、`actor_id`、`trace_id`、接入时 context |
| 状态 | `accepted/duplicate/expired/conflict/rejected/superseded` 和原因 |

来源与执行身份由服务端认证映射；模型或客户端自报的 `source=measured` 不能自行提升验证等级。

### 5.2 更新规则

1. 验证角色、场景、区域、单位、时间和标定，再登记原始记录。
2. 同 ID 同内容返回已有接收结果，不重复更新观测版本或触发续接。
3. 按来源、区域和场景声明的时间窗分组。同源连续帧默认采用组内最新有效证据；不能当成独立观测连乘似然。
4. 新证据替换旧证据时，从先验及当前有效证据集合重建信念；不要在已经包含旧证据的后验上继续叠加新证据。
5. 不同来源也可能相关：声明分组假设；未知关联不包装成独立性已验证。第一版采用保守分组，并做相关性错配压力实验。
6. 冲突记录不删除。区分同时间冲突与状态随时间变化；冲突处理由确定性规则执行，必要时要求第二来源核验或人工处理。
7. 过期、拒绝证据可查阅，但不参与当前有效信念。没有有效证据时退回配置先验，并继续遵循安全域的数据可信度门槛。
8. 只有有效信息变化才递增观测版本并触发再评估；接收重复消息本身不改变 context。

旧版 50/50 混合规则作为历史实现记录。新策略若保留折扣，必须将系数写入场景并通过实验解释；不把折扣后的分布称为精确贝叶斯后验。

验收：重复 100 次不增加有效证据数量；过期证据不解除 DEGRADED；乱序接收不覆盖较新记录；替换前后重算一致；一个区域补证不清除其他区域缺口；冲突能回溯两条原记录。

## 6. W3：真实 AgentArts 编排与共享工具

### 6.1 契约核验与最小接入

本次查阅的华为官方文档已提供运行时调用接口 `POST /runtimes/{runtime_name}/invocations`。应从租户发布页取得实际端点、运行时名和应用类型，保存脱敏请求/响应样本；现有模板路径不得冒充官方契约。[官方调用文档](https://support.huaweicloud.com/api-agentarts/InvokeRuntime.html)

API Key 方式使用 Bearer；会话头、入参和输出解析按具体应用验证。工作流输入与用户代码托管应用的输入结构不能混用。[官方认证与调用示例](https://support.huaweicloud.com/api-agentarts/agentarts_07_0035.html)

接入步骤：只读查询成功 → 工具 Schema 与角色测试 → 待审批工单 → 人工处理 → 反馈续接 → 故障恢复。每步保留平台实际 ID 与本地 ID 对照。

远程 MCP 优先接入现有 Express 服务并注入同一 `MvpService`，复用 `tools.ts`。传输方式根据租户支持与 SDK 契约测试确定；不能假定任意 HTTP 服务就是 MCP。如租户接入不匹配，API 插件桥接同一 ToolRegistry，明确记录采用何种方式。[官方自定义 MCP 文档](https://support.huaweicloud.com/lowcode-agentarts/agentarts_05_0136.html)

stdio 保留为开发客户端入口，不作为共享生产状态的另一写服务。云端身份固定为受限 agent，不能从工具参数传入管理员角色。

### 6.2 平台工作流

```text
接收业务事件 → 读取当前上下文 → 查询有效证据/人员/工单
→ 调用确定性调查评分 → 选择允许动作并解释引用
→ 创建 PENDING_APPROVAL → 持久化等待并结束当前 HTTP 调用
→ 人工审批/派发/反馈 → 可靠事件触发新一轮平台调用
→ 重读上下文与证据 → 再评分/转人工/结束
```

平台负责实际任务理解和工具编排；本地负责身份、预算、工单、证据与安全判定。不能让本地完成所有业务后仅向平台请求总结，却把它描述为平台编排。

拟增只读工具 `evaluate_investigation_options`、`get_evidence_history`、`get_run_status`；写操作沿用现有创建待审批工单工具。先复用现有能力，避免同义工具重复注册。每个工具声明 input/output Schema、角色、超时、审计字段及幂等规则。

解释输出使用结构化字段：事实引用、缺失信息、候选动作 ID、评分版本、推荐理由、下一责任人、等待条件。不允许生成新的容量、人数、概率或评分。无引用的数字不进入正式决策依据卡。

### 6.3 三种状态分开

| 维度 | 设计 |
| --- | --- |
| 安全状态 | 仍为 DEGRADED / REJECT / REROUTE / NORMAL，由安全内核决定 |
| 业务会话 | CREATED / RUNNING / WAITING_APPROVAL / WAITING_EVIDENCE / COMPLETED / NEEDS_HUMAN / FAILED / CANCELLED |
| 平台证据 | 当前可达性、最近成功调用、最近工具调用、完整闭环验证时间、对应应用版本 |

健康探测只更新可达性；历史闭环证据在当前平台不可用时仍可查看，但界面必须显示不可用。平台版本变化后历史证据仍属于旧版本。平台故障不直接改写安全四态；缺失或过期观测依然由安全域触发 DEGRADED。

### 6.4 有界运行与恢复条件

配置每次平台调用的最大步骤、超时、请求预算、同一工具重复上限和无进展上限；数值在 pilot 后冻结。检测工具及参数重复且 context 未变时停止循环。人工等待不保持长连接；超过等待时限转人工处置，不替人审批。

HTTP 200 不等于任务成功；需解析完成/失败事件并读取业务后置条件。流式返回必须测试分片、断流、完成标记缺失与混合错误。超时后的写操作状态标记为待查询，不直接重放。

验收：平台 Trace 能证明真实工具调用；网页和 MCP 看到同一工单；非法工具/角色阻断；等待后使用最新 context；平台不可用时人工流程仍能完成，并记录平台步骤缺失。

## 7. W4：事务、幂等、事件与重启恢复

### 7.1 单实例事务存储

现有 `ops.ts` 已有 JSON 快照和幂等映射，不重复造基本工单功能。为跨工单、预算、会话和待发事件的原子性，拟采用单实例 SQLite 事务存储；具体驱动先验证当前 Node 与 Windows/Linux 兼容，再锁依赖。暂不引入 Redis、消息队列集群或多服务拆分。

最小表：`work_orders`、`run_sessions`、`evidence`、`resource_reservations`、`idempotency_records`、`outbox_events`、`processed_events`、`context_snapshots`。关键数据带 schema 版本、更新时间和乐观锁 revision。

将旧快照导入工具设计为显式执行、可预览、可回滚：备份原文件 → 校验 → 事务导入 → 对账数量/ID/状态 → 切换读取。新状态产生后回滚需导出差异，不直接恢复旧快照丢弃新工单。

### 7.2 幂等语义

- 业务幂等键由服务端稳定生成，包含场景、业务运行、逻辑步骤/意图版本；同一写请求重试沿用原键。
- 唯一约束绑定调用主体、工具、键；保存规范化参数哈希。同键同参返回同结果，同键异参返回冲突。
- 工单、预算预留、幂等结果和 outbox 事件在同一事务提交。
- 请求超时后先按键查询结果；仅明确未发生时才重试。不能用新的 UUID 绕过幂等。
- 分布式调用采用至少一次传递加幂等消费，不声称网络层 exactly-once。

### 7.3 事件与业务一致性

事件包含 `event_id`、aggregate ID/revision、事件类型、context、产生时间、关联 run/work_order/evidence ID。后台轮询 outbox，有限重试、退避、失败转人工；该可靠事件处理是系统业务实现，不依赖聊天自动化。

收到事件后先查已处理 ID，再读取当前业务状态。旧版本事件只审计，不倒退状态；事件不是授权。审批通知不得直接完成派发，反馈通知不得伪造现场观测。

现有工单状态机尽量保留；如新增取消状态，必须列明允许来源状态、权限、资源释放和在途处理方式。业务会话 COMPLETED 与安全 NORMAL 无必然关系：正确地结束于 DEGRADED + 人工接管，也可以是任务完成。

### 7.4 重启规则

恢复工单、人员占用、预留、已处理事件、会话、证据与版本快照；重新检查证据时效。若安全域快照不完整或参数版本不兼容，则递增恢复 epoch、标记旧审批 stale，等待重新评估。禁止计数器归零后碰巧与旧 context 相等而恢复授权。

网络调用不放在数据库事务内；先提交意图，再调用，再落结果。崩溃点至少覆盖事务前、事务后响应前、平台调用后落结果前、事件发布后标记前。

验收：每个崩溃点恢复后无重复生效工单、无凭空释放在途人员；存储失败不能向客户端报写入成功；新鲜度到期会降级；关联 Trace 可追踪恢复过程。

## 8. W5：公平实验与研究主张

### 8.1 环境和策略彻底分离

拟新增 `backend/scripts/experiments/voi-v2/`：环境、策略适配、运行器、指标、报告分别组织；具体场景和实验参数放入 `data/scenarios/` 的实验场景 JSON。保留旧脚本和报告，不用修正后的新结果覆盖旧结果。

环境内部持有隐藏状态、动作真实覆盖、观测采样、延迟、失败和实际成本。策略只接收过去获得的证据、公开动作描述、预算与时间。策略选择相同物理动作时，由同一环境规则决定可获得证据，不能按策略名称缩减覆盖。

随机流用 `seed/episode/action/region/attempt/time_bucket` 稳定索引；共同外生事件共享，未执行动作的观测不泄露。动作可能影响环境时，后续轨迹允许分叉，不能强制共享已经不一致的状态。

观测从概率分布采样，失败显式计费；重复证据由共同来源生成。评估器可见真值但不能调用策略后验当真值。实验 fixture 特别验证：策略接口访问不到隐藏状态，同动作同条件分布不依策略变化。

### 8.2 比较组

| 组 | 定义 | 用途 |
| --- | --- | --- |
| B0 | 不新增调查、使用当前信息决策 | 衡量调查是否值得 |
| B1 | 固定巡查顺序 | 现有业务基线 |
| B2 | 随机选可行动作 | 检查算法是否仅靠多做调查 |
| B3 | 风险优先 + 成本/可达性规则 | 强工程基线 |
| B4 | 单目标 VoI，仍获得动作实际覆盖的全部证据 | 隔离目标函数差异 |
| B5 | 公平环境下的现有多区域 VoI | 新增机制的直接基线 |
| T | 多区域 VoI + 证据生命周期 + 执行前约束 | 候选改进 |

所有组同一动作库、观测权、最大资源、截止时间和硬安全约束。安全预算约束不为消融而在在线系统关闭；旧版越界行为只在离线缺陷复现中展示。可加小规模穷举/先知参考上界，但明确其拥有额外信息，不作为普通可部署对手。

有效消融：T 去同源分组、T 去有效期处理、T 使用固定核查目标；每次只改一项。参数来源与其他模块保持一致。新机制没改善时保留结果，并区分可靠性收益与算法收益。

### 8.3 主指标与样本设计

主指标：截至预定时限，在隐藏真值下的归一化终端决策损失。决策集合必须包含“延后/升级人工”，并预先定义其成本，避免靠无限弃权获得低错误率。损失矩阵来自冻结的场景或专家偏好，不根据胜负调整。

次指标：有效核查完成率、错误建议、未决任务、漏核查、最坏区域损失、人员分钟、实际资源、超预算、截止超时、重复核查。内部熵和后验风险只作解释指标。

计划开发 pilot：10 个开发种子 × 10 episode；正式主实验：30 个互不重叠测试种子 × 40 episode = 每策略 1200 episode。7 组共 8400 个策略 episode，配对单位仍是 1200 个环境实例，不能宣称 8400 个独立环境。种子列表、配置哈希、协议在正式运行前冻结。

主比较预先指定 T 对 B3、T 对 B5；T 对其余组作为次要比较。报告成对差值、按 seed 聚类的 95% Bootstrap 区间、每个种子分布和绝对效应；若进行显著性检验，对主比较进行预声明的多重比较校正。不要只报显著的组。

计划预算曲线采用 3 档预算与 3 档截止时间；先在 pilot 检查可行性，再冻结取值。敏感性包括失败率、延迟、来源相关性、先验/似然错配、覆盖不确定性、人员不足与拓扑变化。每次改变单因素；仅对少数关键因素做预声明交互实验，避免无限参数网格。

环境参数与策略认知参数分离；测试包含未参与调参的拓扑/参数族。合成训练与测试即使种子不同，也不等于真实外部验证。

### 8.4 判定与负面结果

- 是否支持优势，以预先指定指标的绝对差、区间与实际意义共同判断；不以总收益倍数替代成本控制。
- 若区间跨零，只报告未发现明确优势；不能将“不显著”解释为等效。
- 若仅在高缺失或高重复证据条件下改善，主张缩小到该条件。
- 失败、超时、不收敛都进入分母；缺失观测按预声明规则处理，不静默丢行。
- 算法评估使用同一正确实现的资源层；工程安全缺陷不包装为算法比较优势。
- 若 T 不优于 B3，优先分析为何：参数假设、动作库区分度、环境难度、决策损失是否有意义。修改后形成新版本、新协议，旧结果保留。

## 9. W6：真实用户价值与感知边界

### 9.1 先明确工作任务

访谈计划 3–5 位值班/巡查人员，逐项记录：触发条件、现有沟通工具、谁决定优先级、谁派发、反馈内容、常见重复工作、典型耗时来源、失败如何处理。请参与者确认记录；不能把访谈意向计入效果证据。

选择一个可管理的真实区域集合，按实际资料建 JSON；未知容量保持 unknown，真实地名不提升合成参数等级。无法标定通道时，先验证核查任务，不验证疏散路线效果。

### 9.2 受控交叉任务协议

计划 8 位非开发者参与者，每人完成 6 个正式任务，人工原流程和原型各 3 个，总计 48 次任务。48 次不是 48 个独立参与者。提前做独立训练任务，不计入正式结果。

建立 A/B 等价任务对，覆盖观测缺失、重复告警、反馈冲突。每人不重复同一具体案例；分层随机分配流程顺序和案例版本，尽量平衡熟练度与任务难度。时间起点为可见任务发布，终点为符合预定义标准的核查结果；失败按截止时间标为未完成，不能只分析成功者。

人工基线保留人员熟悉的电话/对讲/消息工具与同等可得信息；原型不能获得人工组没有的现场真值。独立观察者使用固定清单判定结果，可行时对条件隐藏；无法盲法时在报告说明。

主指标：每位参与者在两种流程下的任务时间差，同时报告完成率。次指标：漏项、错误建议、重复沟通、求助次数、理解评分与简短访谈。按参与者聚类汇总，展示每人结果；8 人仅作探索性验证，不足以证明错误率不增加或广泛推广有效。

“时间减少 20%”沿用为产品目标，不是已有效果，也不是统计成功门槛。若出现新类型严重操作错误，先修复再开展新一轮；原轮数据保留，不与修改后结果无标记合并。

### 9.3 现场数据表与质量

字段：匿名 participant ID、角色经验、任务 ID/版本、条件、顺序、开始/结束/截止、是否完成、错误类别、求助、证据 ID、工单 ID、观察者、排除原因。排除规则在正式任务前冻结，只排除预定的非研究因素，并报告数量。

公开视频、现场受控记录和合成注入分目录保存；原始个人信息、原始视频按获准范围受限存放，公开仓库只放脱敏数据与处理脚本。证据可审查不意味着必须公开所有人员信息。

### 9.4 视觉与预测分阶段

当前 Part A 官方权重评测保留。第一轮无需自训练模型；能接入合法来源的现场回放，则按视频/机位/日期划分开发与测试，禁止相邻帧随机拆分。记录计数误差、密度段、遮挡、失败帧与标注一致性，不能只挑清晰片段。

人数到区域密度需要 ROI、面积、视野覆盖和标定，缺任何一项不提升可信等级。视觉输出与人工估计都保留不确定性；场馆未标定输入继续 DEGRADED。

预测继续严格滚动评估；后续增加按场景/预测步长的覆盖率与区间宽度、Persistence/季节基线。测试集不得用于校准区间。正式改善前不把预测区间用于新的安全告警阈值。

## 10. 平台评测与故障验证

### 10.1 平台 E1

独立于开发样本，计划冻结 40 个任务实例，各重复 3 次；正常、信息缺口、冲突、工具失败、等待、上下文变化分层分配并记录数量。120 次运行不当作 120 个独立场景。

对照：同租户同模型、同工具权限与调用预算的普通工作流；本地确定性流程作为额外参考。工具 Schema、上下文输入和失败处理机会保持可比。工作流/提示词版本在测试前冻结。

成功由工单状态、权限、证据与事件后置条件判断。正确等待、正确拒绝、正确升级人工可算对应任务成功，不能把一切结束都要求产生路线。记录任务完成、错误工具、阻断越权、重复副作用、恢复、人工介入及成本。

### 10.2 故障 E4

计划 10 类 × 6 个边界变体 = 60 个用例；每类独立列分母与结果，不用总数掩盖缺失类别。

| 类别 | 重点变体 | 不变量 |
| --- | --- | --- |
| 权限与注入 | 冒充 admin、跨 staff、工具返回夹带指令 | 未授权审批/派发/反馈不发生 |
| 幂等 | 响应丢失、重复请求、同键异参 | 同业务副作用不重复 |
| 预算 | 边界、并发、预留过期、实际超时 | 准入不超限；实际超支如实记录 |
| 证据 | 重复、过期、同源、冲突、乱序 | 无虚假置信提升 |
| context | 审批后观测/约束/场景变化 | stale 不自动执行 |
| 人员 | 已占用、技能不符、不可达 | 不派发给不可用人员 |
| 平台 | 401、429、超时、断流、无完成标记 | 不伪报成功、不伪装本地为云端 |
| 存储 | 事务失败、损坏快照、重启 | 不丢已确认状态、不恢复旧授权 |
| 安全内核 | unknown、容量 null、违规候选 | Validator 独立拒绝；四态保持 |
| 浏览器与网络 | 重复点击、断线重连、旧页面 | 后端判定为准，界面不展示假成功 |

未授权操作生效、重复派发生效、stale 绕过、未校验路线显示有效均为发布阻断。样本内零违规不宣称现实零风险。

## 15. 30 天后向国赛强化

先过 G6，再安排 4–8 周的条件性扩展：第二场地或第二活动独立任务验证；扩大用户样本并基于 pilot 估算检验能力；真实视频与参数标定；跨场景迁移成本记录。未通过主链路时不扩大范围。

昇腾作为独立实机里程碑：确认具体型号与 CANN 版本 → 模型转换与算子检查 → 与 CPU 的逐样本数值/计数误差比较 → 相同输入与完整预后处理的延迟测试 → 真实流接入 → 设备日志与模型哈希。功耗只有实际测量才报告。硬件加速不能替代算法或用户价值证据。

长期研究贡献候选是“有时效与相关性约束的主动核查，以及人工审批下的可靠执行”，能否成立由 E2 消融与 E3 使用结果决定。独立校验和权限边界是可展示的系统设计贡献，但本身不等于新算法或安全认证。

## 16. 完成时应能回答的追问

1. 去掉 AgentArts 后失去哪项已验证能力？用普通工作流和本地基线解释，不只展示平台图标。
2. 收益是否来自多用人员或多看区域？展示统一动作环境、预算和实际消耗。
3. 同一摄像头重复上报会不会让系统越来越自信？演示证据替换和信念重建。
4. 创建工单成功但响应丢失怎么办？按幂等键查询，展示只有一个生效工单。
5. 审批期间条件改变怎么办？展示 stale、资源复检和重新确认。
6. 重启后为什么不会执行旧指令？展示 epoch/context、持久化事件和恢复检查。
7. 是否减少真实工作？展示每位参与者结果、失败、实际样本量和局限。
8. 哪些结果没有支持原假设？并列保留 V6.1/V6.2、同预算重试无优势、新实验负面结果。

本方案完成只代表设计已具体化。实机、现场、统计优势与比赛结果均不得提前标记为完成。
